# Derivation DAG from `<>` to finite quantum mechanics: reading note

**AuthorityEffect:** None.

This directory holds `derivation_dag.json`, a derivation graph that starts at the inert inscription `<>` and ends at the state of finite quantum mechanics today. It records what each step rests on and where no source derives the step. It is a map of existing records. It adds no result and promotes no status.

## Model and shape

- The format is the one in `mub6/research/derivation_dag_20261011.json`. The path `external:git-tree:6d3d4b020502661a64322af8941e2ac726338f4b` named in the request does not exist on main, so that file is the model.
- Nodes carry id, stage, status, source_status, statement, source (file:line or ledger row), lean, rust, imported_structure, bottleneck and tags.
- A route lists the inputs it needs together and one output. Routes with one output are alternatives. A route with status `GAP_NO_DERIVATION` carries no source: it marks a link that no record derives.
- Node statuses are ADMITTED_PRIMITIVE, DEFINITION, PROVED_PROSE, PROVED_LEAN, COMPUTATIONALLY_CHECKED, CONDITIONAL, IMPORTED_ASSUMPTION, OPEN, REFUTED and SOURCE_RECORD. Route statuses are DERIVED_PROSE, DERIVED_LEAN, COMPUTED, CONDITIONAL_ON_IMPORT, GAP_NO_DERIVATION and RECORD_PARENT.

## Single source and generated views

`derivation_dag.json` (schema `derivation_dag.v2`) is the single source of the derivation graph. Besides `nodes` and `routes` it holds:

- `records`: every TFQ record of the derivation tree, in reading order, with the fields each record has always had (`coda_atlas_ids`, `coda_atlas_paths`, `existing_derivation_dag_ids`, `f004_refs`, `id`, `lean4`, `local_id`, `name`, `obligation`, `parent_id`, `python`, `record_status`, `rust`, `source_slice`, `stage`, `summary`, `uuid`, and `pfp_review_refs` on reviewed base records);
- `index_document`: the hand-authored text of the Markdown index. `header_markdown` is the title and introduction, `record_count_note` follows the record count, `stage_index` lists the trunk stages in index order, and `coda_atlas_packages` is the Coda atlas package table. Two parts are written by syncs: `application_stages`, by `sync_application_branches.py` from its fragment, and `source_corpus_restatements`, by `sync_unified_dag.py` from `fragments/unified_dag.json`;
- `schema_notes`: this layout, the ownership rules and the run order.

`theory_of_finite_qm.jsonl` and `theory_of_finite_qm.md` are generated, read-only views of `derivation_dag.json`, kept for the readers that use them (receipts, `scripts/build_master_derivation_ledger.py`, the tests, `code/python`, `dag/pfp/generate_prompts.py`). `render_dag_views.py` renders them: the JSONL has one line per record, in the order of `records`, as JSON with sorted keys and non-ASCII characters kept, ended by CRLF; the Markdown index shows the header, the stage index, the Coda atlas table, the record-to-node crosswalk and one section per stage, every per-record line coming from `records` and the nodes. Do not edit either view by hand. The views carry no "generated" banner of their own, because adding one would change their bytes and break the byte identity with the pipeline that produced them before `derivation_dag.json` became the single source; this note and [`theory_of_finite_qm.jsonl.README.md`](theory_of_finite_qm.jsonl.README.md) say so instead. `validate_derivation_dag.py` fails when a view on disk differs from what the renderer makes of `derivation_dag.json`.

Edits: change a node, a route, a base record or the index text in `derivation_dag.json` directly, or change the fragment that a sync owns. A sync owns the records of its `source_slice` (`unified_dag`, `application_branches`, `pregenesis_to_wdp`) and `sync_pfp_results.py` owns the `pfp_review_refs` of base records. `sync_frontier_branches.py` owns the `frontier_branches` slice (see below). `sync_genesis_to_higher.py` owns the `genesis_to_higher` slice. `sync_foc035_observer_presheaf.py` owns the `foc035_observer_presheaf` slice. After a hand edit of `derivation_dag.json`, run `python -I -X utf8 dag/render_dag_views.py --write` (or the full sync cycle below, whose scripts call the renderer).

## One graph: the DAG and the TFQ tree

The nodes and routes of `derivation_dag.json` and its records (shown in `theory_of_finite_qm.jsonl` and its index `theory_of_finite_qm.md`) are one graph. `sync_unified_dag.py`, driven by `fragments/unified_dag.json`, keeps them joined: every TFQ record names at least one DAG node and every DAG node is named by at least one record.

- A record that named no node has a node with the record's own id (tag `unified-dag`) and a route from the node of its parent record. Its status is the record status mapped down, never up: `COMPUTATIONAL_CONTROL` becomes COMPUTATIONALLY_CHECKED, `GAP` and `OPEN_*` become OPEN, and `SOURCE_RECORD` together with the fence labels of a source slice (`FLOAT_SCRIPT`, `EXACT_PROXY_NOT_EH`, `FINITE_TOY`, ...) become SOURCE_RECORD, which carries no derivation status. A route that only restates the tree link is RECORD_PARENT.
- A node that no record named has a record from `TFQ-1000` upward and a generated paper.
- The audited records of four source corpora are application-branch nodes: the fermion sign problem (`papers/core/fsp/`, stage FERMION_SIGN), dimension-six MUBs (`papers/core/mub6/`, MUTUALLY_UNBIASED_BASES), the Majorana problem (`papers/core/majorana/`, MAJORANA) and the Dressing Field Method (`papers/ravera_dfm_dossier.md`, DRESSING_FIELD). Each was audited against the declarations present in this checkout; a node's `source_status` names the status its source claims and the audited status. Records that restate a trunk step are `alias:` tags on that trunk node, listed in the crosswalk section of `theory_of_finite_qm.md`.
- The packet crosswalk of `papers/core/master_derivation_ledger.md` is carried as `packet:` tags. The ledger itself is regenerated from the JSONL view and the DAG by `scripts/build_master_derivation_ledger.py`.

- The 151 reviewed PFP result folders (`dag/results/<NODE-ID>/reviews/`) are carried on their nodes as a `pfp_review` object: the latest review file and its sha256, the verdict, `narrowest_claim`, `does_not_support`, `next_test`, the `scope_effect` (`consistent`, `caveat_added`, `statement_narrowed` or `status_lowered`), the prior status, statement and bottleneck, and any later run that supersedes the review. `fragments/pfp_review_decisions.json` holds the curated decisions and `sync_pfp_results.py` applies them. A node stays PROVED_LEAN only when its statement lies within the review's narrowest claim, or when the cited declaration was read and states it; otherwise the statement is narrowed to the narrowest claim with the unmet part in the bottleneck, or the status is lowered. A status is never raised. A boilerplate `next_test` is replaced by the node's own `does_not_support` obligation. Base records that name a reviewed node carry `pfp_review_refs`, and the crosswalk in `theory_of_finite_qm.md` and the master ledger have a Review column. The review files, the sealed runs and the batch manifests are not edited; later runs and corrections reach the sealed result folders through `reviews/20261021_post_discharge_addendum/`.

Run order after an edit: `sync_pfp_results.py`, `sync_unified_dag.py`, `sync_application_branches.py`, `sync_pregenesis_to_wdp.py`, `sync_frontier_branches.py`, `sync_genesis_to_higher.py`, `sync_foc035_observer_presheaf.py`. Each of them reads and writes `derivation_dag.json` and then calls `render_dag_views.py`, which writes the two views. A new fragment's papers are pinned by operads that `dag/pfp/generate_prompts.py` writes, and `sync_pregenesis_to_wdp.py` refuses an unpinned paper that has no section 4, so after adding a fragment run the syncs, then `generate_prompts.py --write --nodes <the new node ids>`, then the syncs again. Then run `--check` on all seven, `render_dag_views.py --check`, `sync_unified_dag.py --invariants` and `validate_derivation_dag.py --no-files`.
- Nodes named `GP-IMPORT-*` and `L1-IMP-*` are structure the lift or the finite carrier takes in from outside. They are assumptions, not results.
- `see_also` links nodes that two segments each describe. No node was deleted to remove an overlap.

## Validation and limits

- `validate_derivation_dag.py` checks schema, vocabulary, reference resolution, acyclicity, that every derived node has an incoming route, forbidden words, and that cited paths and symbols exist. For the records it checks their fields, unique ids, that each `parent_id` names another record without a cycle, that each record names a node and each node is named by a record, and (when files are checked) that each record has a derivation paper. It checks that the JSONL and Markdown views match the renderer (`--no-views` skips this). It checks structure only. It does not check that a source says what a node says.
- Command: `python validate_derivation_dag.py` from this directory. Expected result: `failures=0`.
- Lean and Rust cells were checked by file and symbol presence, not by building them.
- Some ledgers cite Lean names that are not on disk. Those cells were dropped or left empty and are listed in `segment_notes`.
- The file `derivation_dag.json` is data. Edit the parts a sync owns through its fragments; edit the rest in place and re-render the views.
